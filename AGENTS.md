# Active Writing project instructions

Active Writing (Aw) is a local research and manuscript workspace. The app code is here; manuscript repositories and Aw records are separate. A paper's notes, notebooks, replies and builds live under Aw home's `.paperfocus/project-data/PROJECT_ID/`, not inside its checkout. `project.json` catalogues these records and links them to the paper's registry ID. Use returned paths, not guessed paper-local `.paperfocus` paths. Older PaperFocus names are intentional compatibility names.

For a first orientation, read [the agent guide](docs/AGENT_GUIDE.md): project versus manuscript identity, parent/container TeX detection, section-file creation and guarded undo, readable notes versus notebook evidence, and reciprocal cell/output/passage links. Main-file selection is project-wide, not per-window. Source restructuring requires explicit user scope; never flatten included files or force an undo through later edits.

For research, experiments, simulations, notebook updates or shared-folder replies, read [the research workflow](docs/RESEARCH_WORKFLOW.md). Start with its quick start, then read the sections relevant to the task. Follow the specific saved request's scope; the guide does not enlarge the user's permission.

- Work within Aw's project/conversation structure by default, using files and guarded notebook tools without opening its UI. Keep notes, experiments, evidence links and saved-task completion connected to their owning records; do not turn Aw work into an unrelated pile of files. Reserve opening Aw and checking its renderer for work prepared for the human's review, an explicit display/UI request, or publication presentation checks. Confirm workspace, paper identity/root and intended file; confirm conversation identity for notebook work. Use `awResearch.ts --offline` for saved record reads, guarded cell saves/organization and task completion; no server, HTTP or renderer is involved. With the human's compute permission, `run --offline --allow-python` executes a saved trusted cell in fresh Python and saves displays/provenance directly into its notebook, returning the new revision/run path. `job --offline` reads saved runs, not live waits; shared sessions remain service-only. Keep `--offline` explicit even with a binding. Preflight, evidence snapshots and phase rollover remain service-backed. Do not assume the currently selected paper is the intended one. Before mixed online/offline writes/runs, an older service needs one safe restart to adopt cross-process record/run locks and the shared package overlay; never restart another owner's occupied service. See the agent guide for unavailable-service handling.
- Re-read the owning root's current writing policy in `awResearch.ts inspect` at each new saved request. Research notes are the default: full explanatory notes are allowed within the user's scope, with minimal presentation checks during exploration. Clear intent to read warrants focused readability checks; publication prose requires incremental human review and preserves wording locks. Older conversation context does not override the current policy. Use `awVersions.ts transfer` to preview then explicitly commit notebook moves/copies between existing roots; never relocate records by replacing JSON files.
- Keep notebook research output in the owning conversation and its `.ipynb` cells; longer-form authorized notes may be ordinary manuscript files. Preserve unrelated notes, stable cell IDs, outputs and metadata. Prefer the revision-guarded app stores; do not blindly replace JSON files. An unavailable service is not a reason to stop independent reasoning or ordinary file creation; save a scoped pending artifact without claiming notebook import or task completion.
- Agents can version substantial research phases rather than rebuild archives or rerun saved evidence. `inspect` reports storage headroom and phase lineage. With archival organization authorized, use `awResearch.ts phase --revision REVISION --title TITLE --file HANDOFF.md` to plan, then repeat with `--commit` after saving drafts. It preserves the full old notebook/owner and starts a fresh linked phase; filing alone does not free notebook space. Follow the workflow's rollover/retry rules, preserve partial preparations, and do not version every turn or silently migrate pending tasks. TeX/source restructuring still needs its own scope.
- For the running app, use `scripts/awResearch.ts inspect` with explicit workspace, paper and conversation options. It reads current disk evidence even when a card is closed. Use `cell` for complete source/outputs, `output` for one exact display or control, `put` for a revision-guarded single-cell source update, `organize` for ordering/pinning/filing, and explicit `run`/`job` only within the human's compute permission. See the workflow's fast agent loop; do not treat a bounded summary or plot title as complete evidence.
- Avoid setup/bookkeeping loops: `awResearch.ts --help` works offline without npx/tsx; `discover` lists identities, and `bind --file NEW.json` can retain an explicit confirmed scope (`--scope NEW.json`), not permissions. Use `batch --revision REV --file EDITS.json` to preview related cell changes and `--commit` for one guarded save. Use returned revisions after successful saves; reinspect conflicts, not every mutation. `manifest --file NEW.json` plus `inspect --since NEW.json` identifies changed evidence without claiming it was read. `job --wait-seconds 30` waits without rerunning. Keep a short current-state cell linked to full derivations, not duplicated history. See the workflow for schema/limits. These client features need no restart. Declared-input capture and smaller exact-cell transfer are capability-gated; never restart another owner's occupied service to enable them.
- Run Python only with explicit permission for trusted code. Fresh cells are the default. Optional notebook-scoped shared sessions require deliberate `run --session`; inspect/restart do not execute code. Record setup/run order, restart and replay explicitly for reproducibility. Failures, stops, idle expiry and server shutdown clear state. Simulations are evidence, not proofs. Never invent execution or verification records.
- Runs default to 30 seconds; `--timeout-seconds 120` or `300` requires a deliberate choice within the human's compute permission. Saved parameter sliders select precomputed frames only. Read complete cell outputs, including controls outside the currently displayed frame, before drawing conclusions from a short excerpt.
- Saved `display_heatmap` grids are sample catalogues, not continuous interpolated surfaces. Inspect exact values and extrema; finite samples do not establish sharp constants. `evidence --revision REVISION` creates immutable complete active-cell notebook/text copies with hashes, not automatic uploads or proof verification. Preserve older snapshots.
- Folder-aware research assistants edit the owning notebook directly. Save a Markdown summary cell, then use `finish` with the exact task ID, request hash and notebook revision from the saved request. This records completion in the conversation; no `response.json` is needed. Legacy requests and non-research review/rephrase tasks retain their documented response-file protocol. Web clients still support optional paste or Done without saving reply. An answer arrival offers Return to task; it must not force navigation, approve findings or replace manuscript text.
- During an authorized revision pass, agents may resolve straightforward comments only after verifying that every requested change is fully addressed in the saved manuscript. Leave substantive, ambiguous, partially addressed or judgment-dependent comments open for human assessment. Add anchored assistant comments or replies when the attempt, a remaining concern or a departure from the request needs explanation. Preserve quotes, snapshots and history; use guarded assistance-store saves, never delete comments or bulk-resolve by inference. Resolution is not publication wording approval, proof certification or permission to edit locked text. Explicit comment-only/read-only requests remain read-only.
- Respect hints, reader background and statement-only recovery attempts. Do not read a withheld published proof during an attempt.
- Delegate only when the user or applicable task instructions authorize parallel work. Give workers bounded questions and separate output locations; keep one writer for shared notebook state.
- No direct cloud chat integration, paid model API calls, purchases, automatic dependency downloads, remote publication or Git pushes unless separately requested.
- For explicitly scoped two-machine data reconciliation, read `docs/DEVICE_SYNC.md` and use `awSync.ts` without the service/UI. `checkpoint` captures/stages saved local work once; `changes` reports a bounded index; `conflict`/`file` provide exact scoped material; `reconcile` proposes independent literal text merges or exact-ID decisions. Read only relevant changed material, preserve original packets and use the returned proposal ID with `prepare`. Ordinary proposals never apply live data, approve wording, unlock text, resolve comments, finish tasks or execute cells. Protected/deletion/code-output conflicts retain their own workflow; never replace live stores with detached candidates. `clone` previews then requires exact-plan commit into a NEW, absent data home only; it preserves source/record IDs and policy, creates a distinct device identity and refuses pending requests. App code may be separate: run tools by their code path with the confirmed data home in `--workspace`, never assume the current directory is the data home. Host pairing, uploads, source editing and compute still need their own user scope.

For app implementation, preserve user manuscripts and existing saved work. `problem-lab/` is a separate app, not an automatically synchronized Aw store.

Two-machine research reconciliation now has an explicit `awSync.ts merge` preview/
exact-review commit for ordinary research source, safe existing conversation fields
and notebook evidence. Read DEVICE_SYNC.md first; protected/publication wording,
locks, ownership, request/review/policy decisions, deletions and ambiguous outputs
remain held. Complete batches join history; partial batches do not acknowledge the
remote branch. `checkpoint` remembers its parent and reuses unchanged work; private
`.aw-sync` files carry checked history/unique data, and receive stages only. With a
human-chosen SSH host/data-transfer scope, `pair` pins exact remote tool/home/device
settings without connecting; `sync --peer HASH` previews both copies and
`sync --review HASH --commit` collects both only when the unheld proposals agree.
Save drafts on both copies first. `sync-status` and identical retries recover partial
collections without rollback, repeated code or task completion. A changed copy
needs inspection/fresh review, never a forced retry. No service, public listener,
automatic host-key acceptance, credentials in Aw, or remote compute is involved.

For an explicitly authorized selected-copy import, `awSync.ts collect --path
data/experiments/OWNER/notebook.ipynb` previews one existing experiment notebook;
exact-review `--commit` uses a guarded save, immutable checkpoint and recovery
journal. It never changes source/catalogue/policy/review state, runs code or
completes tasks. Use `collect-status` after interruption: partial live writes may
exist. New local edits stop retries; never force a revision or copy detached JSON
over a store. After collection, stage a fresh local descendant and compare again
before another collection. This is not whole-project synchronization or SSH.
For authorized new branches, `collect --entries ID,ID` adds up to eight new
conversations with distinct new experiment owners. It prepares evidence first,
then appends through byte/revision-guarded catalogue saves. Existing conversations,
source, review/locks and task completion remain unchanged. Ready answers stay
unreviewed without a forced close; queued work is never replayed. New IDs, owner
folders, manuscript roots and original run provenance are checked, not remapped.
Preserve partial bundles, and stage every missing parent before a reverse transfer.

Writing purpose also includes `overview`: a short collaborator-facing README, usually a few paragraphs or about a page, with the aim, main idea, current status and a link to the designated main manuscript/evidence. Do not expand it into a full research note. A coherent draft is welcome within the human's source-writing scope; publication approval is not mandatory. Preserve existing locks and use focused readability checks. Notes remain the default; choosing overview is explicit.

For exploration and research notes, use minimal prose-editing/rendering checks by default: inspect only the changed passage for obvious breakage and fix issues that impede understanding. Do not routinely polish whole notes, compile full PDFs, inspect every page, or run editing/rendering trials. Do deeper writing/typesetting checks only when specifically requested or working on publication manuscripts, and still scope them to the actual change. Spend exploration time on reasoning and useful evidence. This does not relax scientific checks, provenance, complete-output inspection, source-save guards, or the app-code regression requirements below.

A reading-ready request need not use explicit QA language. If the human makes clear that the current version is something they want to read (for example a digest, walkthrough, or current note prepared for their reading), treat that as a request for a focused readability/rendering pass on that version. Make notation and exposition usable and check the relevant display, proportionately. Do not automatically classify it as publication, certify its mathematics, approve every word, or launch exhaustive full-document appearance trials. Temporary working notes remain lightweight until there is this reading signal.

For an incremental manuscript-writing request, read `docs/WRITING_WORKFLOW.md`. Work one idea through at most three connected paragraphs, using saved scope and exact target IDs. Approved wording is locked context, not another rewrite target. `scripts/awWriting.ts inspect` and guarded `submit` import proposals only; do not bypass the human review queue by editing publication source, approving words or unlocking settled passages. Research/notes writing outside an Aw writing round retains its explicit user scope.

Distinguish document purpose: authorized **Research notes** may be a full explanation, derivation or digest at any useful length; the three-paragraph cap and mandatory word-by-word curation are for **Publication drafts** and deliberately chosen small writing rounds. The manuscript menu stores purpose per root, outside its checkout; unmarked roots default to research notes; choosing the Paper scaffold or Publication draft explicitly enables publication guardrails and new versions inherit purpose. `awResearch.ts inspect` reports the conversation's root/policy and `awVersions.ts inspect/purpose` provides guarded metadata access. Do not relabel publication text to evade review. Changing purpose never clears pending reviews, resolves human comments, unlocks wording or grants new source/compute authority. Preserve human work and distinguish proofs, evidence and conjectures in both kinds of document.

For a first real research session, optionally use the scoped `awResearch.ts preflight` command. It checks saved ownership/files and a fixed Python diagnostic, never cell code. Several browser windows should share one Aw service. Local execution defaults to two simultaneous runs in different notebook owners, always one per notebook; `AW_PYTHON_CONCURRENCY=1..4` sets the service-wide limit at startup. Inspect the running service's actual capacity before assuming a slot is free. A rejection does not queue code. Do not stop another owner's run or restart the service to free capacity without authority. Keep one coordinated notebook writer. Read `docs/REMOTE_RESEARCH.md` before adding remote execution: one authoritative Aw host, immutable job inputs/results, guarded collection, explicit resource budgets and no automatic uploads/submission or public listener. Remote compute is not implemented yet.

## Proportional verification and short follow-ups

- Do not repeat a full startup/trial/shutdown ceremony on each small user idea. Continue from the current evidence, batch related edits in the same pass, and recheck only what changed. Never defer a requested change solely to batch it with hypothetical future prompts.
- For routine UI, queue, presentation or launcher work, use `npm run check -- --area ui` (or `queue`, `presentation`, `desktop`; repeat `--area` for multiple scopes). It runs the feature's checks, two deterministic rotating samples of older test files, and an incremental typecheck. Samples supplement targeted tests; they are not full-suite verification. Add a direct regression test for a reported bug.
- Supply touched code paths using repeated `--changed path` when practical. Unknown source/backend/config changes conservatively select the full suite. `--style-only` skips typechecking only for CSS/text-only UI changes. `--plan` prints the plan without running or advancing the sample rotation.
- Source saves, file access/imports, storage, compilation, model execution and research/harness changes require a full checkpoint: `npm run check:full` (or the corresponding `--area files|source|storage|compiler|models|research|harness`). This deduplicates all test files registered in `test` and `test:*`, including workflow and launcher checks. Run a full checkpoint for a cross-cutting refactor, a user-requested full sweep, a release, or when a sampled failure suggests a wider regression. Do not weaken tests to make sampling pass.
- Build at a meaningful checkpoint or when the desktop app needs updated assets (`--build` adds the production build), not automatically after each small source-only follow-up. State when desktop assets still need a build. Do not rebuild unchanged code or repeat a typecheck immediately after a build that already includes it. A docs-only follow-up needs no browser or production build.
- Use one bounded, focused browser trial when an interaction/layout change needs it; don't replay the full suite of UI journeys by default. Keep an existing owned, isolated trial server only while needed; never restart or change the user's main app merely for QA. Stop your own unneeded trial server. Record what actually ran and any remaining uncertainty; never describe sampled checks as exhaustive.

Browser editing trials must use an isolated paper workspace and a separate browser origin (see `scripts/uiTrialServer.mjs`). A paper labeled as a trial may still be open in the user's editor. Do not edit it concurrently or change the main workspace's selected project for QA.
